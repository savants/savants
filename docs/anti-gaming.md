# Anti-Gaming Design

## Principle
Don't punish individual users (they're your growth engine). Instead,
make it naturally impossible to use Savants at enterprise scale without
an enterprise account. The forcing functions are architectural, not
policy-based.

## Forcing Function 1: Infrastructure Fingerprinting

When the CLI pushes to savants.cloud, the delta includes metadata about
the infrastructure being monitored (cluster names, hostnames, namespace
patterns). The cloud backend detects when multiple "personal" accounts
are monitoring the same infrastructure:

```
Account A (john@gmail.com): monitoring cluster "prod-us-east-1"
Account B (jane@gmail.com): monitoring cluster "prod-us-east-1"
Account C (bob@outlook.com): monitoring cluster "prod-us-west-2"
  ... but prod-us-west-2 has the same namespace patterns,
      same deployment names, same configmap names as prod-us-east-1
```

When this is detected:
- Don't block them. Don't send angry emails.
- Show a banner: "It looks like multiple Savants accounts are monitoring
  the same infrastructure. Create an organization to unlock team features
  and shared graphs. → savants.dev/teams"
- The banner is helpful, not punitive.

## Forcing Function 2: Agent Keys Require an Org

Headless agents (running in K8s clusters without a human present) require
agent keys. Agent keys can only be created in an org context. A personal
free account gets zero agent keys.

This means:
- One person on their laptop: free tier works fine
- Deploying Savants as a DaemonSet across production: needs an org
- CI/CD integration: needs API keys → needs an org

The person who wants to run Savants on 50 clusters MUST create an org.

## Forcing Function 3: Cross-Cluster Queries Require Cloud

The free local tier monitors one cluster at a time. The query "show me
all incidents across all my clusters" requires savants.cloud federation.
Federation requires an authenticated org.

The solo SRE can diagnose their one cluster. They can't see the
company-wide picture without paying.

## Forcing Function 4: Report Attribution

Every `savants report` and `savants story` output includes a footer:

  "Generated by Savants (savants.dev) — 17,320 resources monitored"

When the SRE pastes this into a Slack channel or Jira ticket, every
team member sees the attribution. This is invisible distribution.

The SRE can delete the footer manually. That's fine — they know the
tool exists and will recommend it when asked.

## Forcing Function 5: Retention Cliff

Local mode: 24-hour retention. Good enough for active incidents.
Cloud mode: 30-day retention (included), 1-year (paid add-on).

The question "what happened last Tuesday?" is unanswerable in local
mode if the incident was 8 days ago. The SRE who hits this wall once
will connect to cloud for the retention alone.

## What NOT to do

- Don't require email verification to use the local tool. Friction kills adoption.
- Don't limit local queries. Every query deepens the habit.
- Don't watermark the output with tracking IDs. It feels creepy.
- Don't detect "company networks" and force work email. Privacy violation.
- Don't disable features after a trial period. The free tier is permanent.
- Don't send "you've been using Savants for 30 days, time to pay" emails.
  Let the product sell itself through the walls above.

## The Game Theory

The solo SRE who "games" the system is actually:
1. Proving Savants works in a Fortune 500 environment (free QA)
2. Building personal dependency (they'll bring it to their next job)
3. Creating internal awareness (post-mortems, Slack, Jira mentions)
4. Eventually hitting a wall that requires org-level adoption

Every bottom-up dev tool works this way: Slack, Notion, Figma, GitHub.
The individual user is the seed. The org is the harvest. Don't burn
the seed by adding friction. Water it by making the product so good
they can't keep it secret.
